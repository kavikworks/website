# Workflow Blueprint sample
**A scheduled quote request, from arrival to an assigned next step.**

Kavik Works | Free planning example | Version 1

This example is for a small home service business using a shared inbox and a spreadsheet. It is illustrative, not a customer case study or installed automation. It does not demonstrate sales or time savings. Review the rules against your own process before use.

## 1. Define the finish line
Every normal quote request has a recorded owner and next action. The office can see what is waiting without searching through forwarded emails. Email triage is not emergency dispatch.

**Workflow map:** Request arrives -> office reviews -> ask for missing details or assign an estimator -> record the next action -> record the known outcome.

## 2. Keep one record
| Field | What belongs here |
| --- | --- |
| Request ID | The original message link or another unique reference |
| Contact and request | Name, business contact method, service location, and a brief description |
| Owner | The person responsible for the next action |
| Status | Needs review, waiting for details, assigned, or closed |
| Next action | A concrete step and a time chosen by the responsible person |
| Outcome | Quoted, booked, declined, duplicate, or unknown |

Capture only what is needed for this workflow. Keep the list accessible only to the people handling requests. Do not copy account passwords or payment details into it.

## 3. Agree the routing rules
1. **New request:** the office checks service area and completeness.
2. **Missing details:** the office asks for the specific missing information.
3. **Ready to quote:** assign one estimator and record the next action.
4. **Duplicate or existing job:** attach it to the existing record.
5. **Unclear, sensitive, or urgent:** route to a person. Keep the existing emergency contact process.

Use a template only when it accurately matches the conversation. Stop follow-ups after a reply, opt-out, completed request, or failed delivery. A draft, attempted send, or sent message is not proof of delivery.

## 4. Set up the simplest version first
1. Create a shared list with the fields on page 1. Limit access to the people handling requests.
2. Agree who checks new requests and who covers absence during working hours.
3. Save the reviewed templates in your existing email tool.
4. Walk through the tests on page 4 manually.
5. Only then consider an integration to copy details or prepare drafts. Retain a review queue for uncertainty and a record of each action.

**Failure rule:** If a tool is unavailable, retain the original message, record what is unknown, and put it in the human review queue. Check the existing record before retrying an action.

**Decisions for your team:** Name the office reviewer, estimator, and absence cover. Choose working-hour review times. Verify who can access the shared list. These are placeholders to resolve before live use, not commitments made by this sample.

## 5. Start with three editable templates
Replace each bracketed detail with information from the actual conversation. Review the recipient and full thread before using a template.

### Acknowledgement
> Thanks for your request about [service]. Our office will review the details and confirm the next step. This message does not confirm an appointment or a price.

**Use when:** the office has received a normal request and can review it. Do not promise a response time the team cannot meet.

### Missing information
> To route this to the right person, could you send [specific missing detail]? Once we have that, we can confirm the next step.

**Use when:** one clearly identified detail is missing. Ask only for what is needed to route the request.

### One optional follow-up
> Would you still like help with [request]? If so, send [specific next detail]. If your plans have changed, no further action is needed.

**Use when:** the request is still open, no reply or delivery failure has appeared, and a follow-up is appropriate. Do not keep nudging after a reply, opt-out, completed request, or failed delivery.

**Keep human review:** Unclear intent, sensitive information, urgency, a disputed status, or an uncertain send result should go to the responsible person. This sample does not make pricing, scheduling, regulated, or emergency decisions.

## 6. Test before connecting live work
Use invented test records, not customer data, for the first walkthrough.

| Test input | Expected result |
| --- | --- |
| Complete normal quote request | Correct owner and next action are recorded |
| Missing service location | Ask for that detail; do not assign blindly |
| Same message processed twice | One record; no second reply |
| Reply, opt-out, or bounce appears | Further nudges stop; status is reviewed |
| Required tool is unavailable | Original request stays visible for human review |
| Urgent or unclear request | Existing human contact process is used |

Record pass or the specific defect for each test. Correct defects and rerun the affected case before connecting live work.

## 7. Measure whether it helps
For one normal working week, record requests received, requests without an owner, time to a useful first reply, minutes spent handling requests, and known outcomes. Keep unknown outcomes separate.

Compare a similar week after the change. Use actual counts and time; do not attribute extra sales without evidence.
